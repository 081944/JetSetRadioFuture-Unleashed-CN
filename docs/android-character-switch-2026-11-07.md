# Android 按钮切换角色：实现与验证

已接入“按钮请求 → 单角色异步加载 → 按当前位置重建玩家 → 核验镜头和资源绑定”的实现。副屏底部显示已解锁角色按钮，主屏设置中也有“切换角色”；主屏选中角色后关闭对话框，让游戏恢复运行并处理请求。可以再次选择原角色，走同一条流程切回。第 32 版已打包安装并确认基本往返切换；用户反馈偶发腾空后落地，物理状态衔接仍待修复，详见文末。

实现仅支持当前 CN profile、单玩家槽 0 和正常自由行动状态 15。暂停地图（110）、剧情、加载、拍照模式、角色对象或场景不一致时不执行换人。切换保留位置和朝向，动作/速度由原版构造流程重新初始化，不承诺空中或磨轨动作连续。

## 源码入口

- `launcher/android/java/com/jumatt/jsrfunleashed/CharacterSwitchBar.java`：已解锁角色按钮、当前角色及加载/失败反馈，离开窗口停止轮询。
- `port/android/jsrf_android.c`：JNI 只交换请求和复制状态，不从界面线程访问 guest RAM。
- `port/android/character_switch.c`：游戏线程上的加载、删除等待、重建和恢复状态机；互斥快照与原子请求邮箱隔离两个线程。
- `port/recomp_manual.c`：完整主循环返回后推进状态机；交接期间暂停 flow 控制器并屏蔽手柄输入，保留加载器；管理器析构完成后通知状态机。新增 guest 调用保存整数、x87、SSE、标志和 SEH 桥接状态，明确区分 cdecl 与 thiscall 并核验 guest 栈清理。

| --- | --- | --- |
| `sub_000A8370` | 每帧遍历 32 个玩家槽；读管理器变量 `0x6D+i` 请求、`0x2D+i` 编号、`0xAD+i` 配置，查询对象表 `0x0C+i` | 有现成生成请求入口，但不是独立完整的换人 API |
| `sub_000A6980` | 创建玩家管理器，再调用 `sub_00084200` 创建玩家；玩家对象另行登记到对象表的动态编号 | 不能假定槽 0 的对象表项目就是玩家本体 |
| `sub_00084200` | 配置记录 `+4` 写入玩家 `+0xFBC`，随后按这个编号调用 `sub_00025700(1,id,6,0)` 和 `(1,id,7,0)`，绑定模型、动作/属性相关指针，并调用 `sub_0009CC40` 初始化其他资源 | 完整换人必须处理整套资源及对象生命周期；改 `+0xFBC` 不足以换模型 |

| 摄像机对象 `+0x24` | 当前副屏快照由此找到玩家 | 玩家替换后须核验镜头和副屏是否跟随新对象 |

全局管理器为 `*(0x22FCE0)`；变量区基址为 `root + 0x7868`。这些观察来自当前 CN 生成代码，不能直接套用其他版本。

## 资源加载：已经定位到具体入口

| 调用/字段 | 行为与约束 |
| --- | --- |
| `sub_000256A0(2, id)` | 单独加载目标角色；最终分派到 `sub_00031490`，更新函数是 `sub_00032C70`。已有精确 ID 的记录时只设置保留标志；否则新增 `0x660` 字节记录并开始异步加载 |
| 资源管理器对象表编号 `7` 的 `+0x44` | 全局加载器忙碌状态；忙时提交会返回 0。提交成功不等于加载完成 |
| `sub_000256C0(2, id)` | 分派到 `sub_00031500`，查询精确 ID 是否已经进入完成列表；不检查全局加载器是否空闲 |
| `sub_00025700(1,id,6,0)` / `(1,id,7,0)` | 解析模型及属性数据；对应 `sub_00032610`。先精确匹配，再匹配记录 ID 低 8 位；私有资源为空时可回退到共享资源 |
| `sub_00032790` | 资源回收，包含共享引用计数、音效和私有记录销毁。记录 `+0` 和 `+4` 参与两阶段保留判断，不是可任意改写的简单引用计数 |

`sub_00032C70` 的状态 0–12 加载共享角色库、角色 `.bin`、`.dat` 和音效；结束时把新记录追加到管理器 `+0x1E4` 链表并写入 ID。没有看到它在这个入口中先卸载当前角色，所以它是“保留现玩家并预加载目标”的候选路径。仍需运行验证内存余量以及与场景资源回收的协调。

完成条件应同时检查：加载器空闲、精确目标 ID 已驻留、两个 getter 返回有效地址。检查工具输出的 `resources_ready` 只表示这三项满足，不保证构造器所需的所有其他资源和副作用已经验证。

不要用命令 1 代替单角色加载：命令 1 的 `sub_000320A0` 会遍历变量 `0xD..0x10` 的四个选择槽，与独立预加载的范围不同。

## 已解锁角色与按钮编号

`sub_00039D10(this=0x1EFFB0,id)` 查询 `this+0x14` 的解锁位。原版菜单的顺序不是角色 ID；按钮必须传入角色 ID，不能直接传菜单位置。

菜单顺序到 ID 为：`0,2,1,3,9,8,4,10,6,5,20,21,12,16,14,13,15,11,17,23,19,7,18,22`。

原版菜单确认函数 `sub_0011B290` 主要写变量 `0xD` 和确认标志，没有替换现场玩家。只调用它不足以完成换人。

本地地图 27 的 RAM 抓取中：当前玩家 ID 为 `6`（Yoyo）；解锁位为 `0x46`，解锁 Corn（1）、Gum（2）、Yoyo（6）；资源链只含 Yoyo，加载器空闲。Corn/Gum 按钮需要先经过预加载。抓取时 flow state 为 110；这不能作为允许自由行动换人的状态白名单依据。

## 玩家删除与重建的边界

`sub_00013FC0(object_id)` 查询对象、调用 `sub_00011BE0` 标记自身并解除更新/绘制关联，再对 `+0x28` 子链调用 `sub_00011C20`。后者递归标记子对象并清除对象表项目。最终析构由调度器 `sub_00011D00` 等遍历路径执行，不是标记后立即全部释放。

已核验的原始尾跳：

```text
0x11C00  mov eax,[esi+8]       ; 对象编号
0x11C03  pop esi
0x11C04  mov [esp+4],eax      ; 用对象编号替换参数
0x11C08  mov ecx,[0x22FCE0]
0x11C0E  jmp 0x12890         ; 清对象表，尾调用负责返回
```

完整生成 C 已包含 `g_seh_ebp = ebp; sub_00012890(); return; /* tail jmp */`，与上面的指令一致，无需替代或修复。此前调查脚本过滤所有以 `g_seh` 开头的行，连同行内的尾调用一并隐藏，造成“缺失尾跳”的误判；已以完整生成函数核实并更正，没有改动该删除函数。

生成器 `sub_000A8370` 在对象表 `0x0C+slot` 为空时才创建新管理器；仍有旧管理器时只调用 `sub_000A6B10` 更新配置，角色资源不会重绑。因此不能仅更新 `0x2D+slot` 再提交请求。

请求变量 `0x6D+slot` 必须是 guest 内的 52 字节配置记录地址，不是布尔值或 host 指针。原版生成器把配置复制到自己的持久缓冲区，再构造管理器、玩家及关联对象。应沿用这条路径，不在旧玩家内存上重跑构造器。

## 已接入的执行次序

1. 角色按钮通过 JNI 提交编号。在删除开始前连续点击取最新请求；删除开始后的新请求留到当前交接结束再处理。
2. 每帧结束检查 CN 对象类型、单玩家槽、角色选择变量、场景和生成请求。界面只展示锁保护的状态副本。
3. 在加载器空闲时提交一次命令 2；最多等待 30 秒，继续让游戏加载器更新。目标 ID 精确驻留且模型/属性地址有效时才推进；预加载失败保留原玩家。
4. 复制正常配置（首字为 0）、原位置和朝向。通过 `sub_00013FC0(12)` 标记旧管理器树；在当前帧结束、没有对象遍历的时段，用 `sub_00011B90(this=manager,children)` 析构其子树，再调用 `sub_000A6AF0(this=manager,1)`。这与原版 `sub_00011D00` 标记删除分支的子对象优先次序一致；不额外遍历其他兄弟对象。确认 `sub_000A6110` 完成通知，以及管理器、玩家和镜头对象表均清空；不能仅凭对象表为空就认为析构已完成。
5. 把 52 字节配置写入仍属于原生成器的持久槽 0 缓冲区（`spawner+0x544`），更新变量 `0xD`、`0x2D`，提交 `0x6D`。不用 host 指针或临时 guest 栈地址。
6. 同一帧边界调用原生成器 `sub_000A8370(this=spawner)` 创建管理器、玩家、镜头，正常路径在下一轮世界更新前已有新玩家。下一次检查核验 ID、镜头父玩家，以及模型 `+0x2A4/+0xC90`、属性 `+0x58` 与资源记录吻合后结束交接。再点原角色会重复该流程。
7. 生成请求被消费却没有管理器时，在同一边界立即尝试原角色重建；若 5 秒后资源绑定/镜头仍不正确，也尝试一次原角色重建，部分创建的管理器先正常删除。若旧管理器析构超过 5 秒仍未完成，显示失败并继续等待，避免在旧存储上强行重建；场景身份改变时取消旧事务。无法恢复时需要重新启动游戏。

原生成器不能在同一玩家槽提前创建第二个管理器，所以这不是原子的无损替换。新增角色资源由原版资源管理器保管，切换过程中不主动卸载旧角色或改解锁位；场景资源回收仍走原版逻辑。多次切换后的内存余量、镜头行为、任务脚本引用、碰撞、音效及喷漆仍需实际游戏验证。

## 第 33 版：场景碰撞初始化与副屏气泡

32 版只读采样 `build/logs/character-switch/32-motion-switch.bin` 中，静止连续换人的世界高度基本维持约 185.019，局部沉降约 0.071；部分新玩家却进入 `E50=15/E58=11`，随后进入 `E50=16/E58=3`。完整生成源码显示该路径由 `sub_00080340` 检测 `player+0x3C8` 接收器事件触发，事件类型 2 调用 `sub_00092750`。它并非单凭高度变化进入的普通下落状态。

`sub_00024AB0` 分配并注册 0x68 字节场景区域接收器，只初始化链表和事件标记，未初始化前 0x30 字节检测轨迹。原版正常生成时依赖任务顺序；当前帧末即时重建后，区域检测任务可能先于新玩家更新，读到回收内存中的旧轨迹，误触发弹起/复位区域。修复在原生成器返回后、任何世界任务更新前，调用玩家原本使用的 `sub_0006F890(this=0x1EC050, receiver, previousPosition, position)` 发布初始轨迹并清理事件标记，保持接收器链表不变。没有禁用真正的场景区域检测，也没有改写生成 C。初始化调用失败不会报告切换成功，仍走原有恢复流程。

副屏改为右下角竖排 64 dp 圆形角色气泡，当前角色青色高亮，状态显示在上方的小气泡内，角色较多可滚动（高度不超过副屏的 62%）；主屏设置中的横排入口保留。按钮之外继续由原地图处理触摸。

## 第 38 版：完整出生轨迹初始化
